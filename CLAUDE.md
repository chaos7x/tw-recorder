## Versioning

`pyproject.toml`'s `version` field and the actual released version are two separate things: `docker-release.yml`'s `build-and-push` job derives the shipped version from `git describe --tags` (auto-incrementing the patch component from the latest `vX.Y.Z` tag), not from `pyproject.toml`. Before bumping `pyproject.toml`'s version for a change, check the latest real release tag first (`git tag --sort=-v:refname | head -1`) rather than just incrementing whatever value currently sits in `pyproject.toml` — if that value is already ahead of the latest tag (e.g. a previous PR in the same release cycle bumped it but nothing was tagged/released yet), fold the new change into that same still-unreleased version instead of bumping again, to avoid a phantom intermediate version that never shipped. See README.md's "🏷️ Versionierung" section for the full release/tagging scheme, including the reserved 4th version digit for OS-patch-only releases.

## Backlog / Ideen

- **Live-Multicast-Relay parallel zur Aufnahme (Kandidat für 2.x):** Twitch-Live-Streams zusätzlich per Multicast (UDP, z.B. via `cvlc`) im LAN verteilen, während tw-recorder ganz normal weiter aufnimmt (inkl. Werbeerkennung/-Schnitt). Aktuell nicht möglich, ohne den Stream zweimal von Twitch zu ziehen (doppelte Bandbreite): `record_loop()` baut sein Streamlink-Kommando intern selbst und schreibt immer direkt in eine `.ts`-Datei (`-o out_pattern`, siehe `recorder.py`) - es gibt keinen Pipe-/stdin-Modus, über den ein zweiter Verbraucher (z.B. `cvlc` fürs Relay) denselben Stream abgreifen könnte. Naiver Ansatz (Streamlink-Ausgabe live direkt in eine FIFO für einen MKV-Muxer schreiben) würde die Abbruch-Robustheit des jetzigen Zwei-Schritt-Ansatzes verlieren: `.ts` übersteht einen abrupten Abbruch (Netzwerk-Hänger, Stream-Ende) trivial und lässt sich danach immer noch verlustfrei zu `.mkv` remuxen, ein live geschriebenes `.mkv`/`.mp4` bräuchte dagegen eine Finalisierung am Ende und wäre bei einem Abbruch mittendrin bestenfalls reparaturbedürftig. Ein funktionierender Ansatz müsste also einen zusätzlichen, parallelen `tee`-Zweig auf eine FIFO öffnen, *ohne* das bestehende `.ts`-Schreiben zu ersetzen - der bestehende Aufnahme-Pfad bliebe unverändert, das Relay bekäme nur einen zusätzlichen, unkritischen Nebenabgriff derselben Daten.
